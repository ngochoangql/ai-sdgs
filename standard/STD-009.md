# STD-009 — VERIFICATION, QUALITY ASSURANCE & RELEASE GOVERNANCE

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-009` establishes evidence-based verification rules, anti-tampering test integrity controls, three-layer quality assurance (`L1`/`L2`/`L3`), and release readiness criteria so neither AI agents nor human contributors can declare software complete, compliant, or releasable without reproducible proof.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Verification Evidence:** Concrete, reproducible output proving a claim (exact shell command executed, exit code, passing test counts, `aisdgs validate` output, build artifact digest, or structured `L3` audit report).
- **Test Tampering:** Deleting, skipping (`skip`/`xit`/`#[ignore]`), mocking out core system-under-test logic, or loosening assertions on an existing test merely to obtain a passing exit code without human-authorized specification change.
- **Semantic Audit Bundle:** The deterministic context package assembled by `aisdgs audit` pairing `git diff` hunks with affected `REQ-*`, `ADR-*`, `CR-*`, and contract definitions.

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`HUM-OWNER` / `HUM-PROD` / `HUM-ARCH`:** Approve release readiness, quality waivers (`EXC-*`), and any legitimate removal/modification of obsolete acceptance tests when requirements change.
- **`AI-IMPL`:** Writes unit, integration, and regression tests alongside authorized implementation code and runs local test/build suites.
- **`AI-VERIFY`:** Executes independent verification checks (`aisdgs validate`, `aisdgs audit`, full test suite) and records factual outputs without altering assertions to hide defects.

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-009-R01` `[NON-WAIVABLE]` — Evidence-Based Completion Law:** An AI agent MUST NOT report any implementation task, bug fix, or Change Request as `VERIFIED`, *"tested"*, *"passing"*, or *"compliant"* without actually executing the relevant verification commands and citing real results. If tests or builds could not be executed (e.g., missing runtime, external service unavailable), the agent MUST report claim state strictly as `IMPLEMENTED (UNVERIFIED)` and explicitly disclose what was not run.
- **`STD-009-R02` `[NON-WAIVABLE]` — Prohibition of Test & Validator Tampering:** AI agents MUST NOT delete, comment out, mark skipped, weaken assertions in, or hardcode return values for existing automated tests—nor pass `--no-verify` to Git commits/pushes—to bypass failures. Modifying an existing acceptance test is permitted ONLY when the underlying `REQ-*` or contract changed under an authorized `CR-*`.
- **`STD-009-R03` `[WAIVABLE]` — Regression & Acceptance Test Coverage for Changes:**
  - Every `BUG_FIX` SHOULD (and in `STANDARD`/`STRICT` tiers MUST, where testable) add or update an automated regression test reproducing the defect prior to or alongside the fix.
  - Every `FEATURE_REQUEST` and `TECHNICAL_CHANGE` MUST include verification evidence demonstrating conformance with the acceptance criteria of all affected `REQ-*` items (`STD-005-R02`).
- **`STD-009-R04` `[NON-WAIVABLE]` — Mandatory `L2` Governance Gate Prior to Closure/Release:** Before closing any `CR-*`, merging to a protected trunk branch (`STANDARD`/`STRICT`), or cutting a release, `aisdgs validate` and `aisdgs baseline verify` MUST execute and return `Exit Code 0` (`COMPLIANT` or `COMPLIANT_WITH_WAIVERS`).
- **`STD-009-R05` `[WAIVABLE]` — Structured `L3` Semantic Audit on High-Impact Changes:** Every `track: FULL` Change Request with `risk_level` of `MEDIUM`, `HIGH`, or `CRITICAL` SHOULD in `STANDARD` tier—and MUST in `STRICT` tier—undergo a structured `L3-Semantic-Audit` (`aisdgs audit --cr <CR-ID>`) verifying that actual code behavior matches prose `REQ-*`/`ADR-*` intent and introduces zero undocumented side effects.
- **`STD-009-R06` `[WAIVABLE]` — Rejecting User Prompts to Skip Mandatory Verification:** If a user prompt instructs an AI agent to *"skip tests"*, *"commit with `--no-verify`"*, or *"just mark the CR verified without running checks"*, the agent MUST refuse to fabricate `VERIFIED` status (`STD-009-R01`, `STD-009-R02`), explain the governance boundary, and either run the checks or record the work honestly as `IMPLEMENTED (UNVERIFIED)` awaiting human handling.
- **`STD-009-R07` `[WAIVABLE]` — Release Readiness & Version Synchronization:** Cutting an official project release MUST verify: (a) clean working tree, (b) `PROJECT-BASELINE.md` in `LOCKED` state (or `ANCHORED` if explicitly permitted in `LITE`/`STANDARD` Brownfield), (c) zero open `IN_PROGRESS` or unreconciled `EMERGENCY_ACTIVE` CRs on the release commit, (d) zero expired `EXC-*` waivers, and (e) synchronized application version, changelog, and baseline version.
- **`STD-009-R08` `[WAIVABLE]` — Pre-Commit & CI Gate Installation:** Adopting projects SHOULD install `aisdgs hooks install` locally (`LITE`/`STANDARD`) and MUST enforce `aisdgs validate` inside automated CI pipelines (`STANDARD`/`STRICT`) so governance checks cannot be bypassed by local developer or agent misconfiguration.

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 Task & Change Verification Workflow
1. Run target language build, linter, typechecker, and automated test suite; capture exact command and exit status.
2. Synchronize affected specs/contracts and run `aisdgs change verify <CR-ID>` + `aisdgs validate`.
3. For `CR-FULL` (`MEDIUM+` risk), run `aisdgs audit --cr <CR-ID> --output quality/reports/AUDIT-<CR-ID>.md` and review semantic alignment checklist.
4. Populate `verification_evidence` in `CR-XXXX.md` with factual command outputs and transition CR to `VERIFIED`.

### 5.2 Release Gate Checklist
1. Execute full test suite + `aisdgs validate --strict` (or standard mode in `LITE`).
2. Execute `aisdgs baseline verify` confirming `0` drifted baseline paths.
3. Generate release compliance snapshot via `aisdgs report --format md > quality/reports/RELEASE-<ver>.md` (`STANDARD`/`STRICT`).
4. Tag release in VCS under `HUM-OWNER` authorization.

## 6. PROPORTIONAL TIER SCALING RULES

| Verification Control | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| Honest Claim Reporting (`R01`, `R02`) | Mandatory (`MUST`) | Mandatory (`MUST`) | Mandatory (`MUST`) |
| Automated Regression Tests (`R03`) | Recommended (`SHOULD`) | Mandatory (`MUST` where unit/integration harness exists) | Mandatory (`MUST` + coverage/trace gate) |
| `L3` Semantic Audit Report (`R05`) | Optional (`MAY`) | Recommended (`SHOULD`) on `HIGH` risk CRs | Mandatory (`MUST`) on all `CR-FULL` (`MED+` risk) |
| Git Hooks & CI Enforcement (`R08`) | Local `pre-commit` recommended | Local hooks + CI PR check **mandatory** | Signed protected-branch CI + `--strict` **mandatory** |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-009-R01`, `STD-009-R02`, and `STD-009-R04` are **`[NON-WAIVABLE]`**. Fabricating test evidence or bypassing `--no-verify` via AI is an unconditional compliance breach.
- Projects targeting hardware-in-the-loop or external mainframes unavailable in local dev environments MAY record `IMPLEMENTED (LOCAL_HARNESS_ONLY)` locally provided CI/staging hardware verification runs prior to `CLOSED` / release.

## 8. THREE-LAYER CONTROL MAPPING

| Rule ID | `L1-Advisory` | `L2-Deterministic` | `L3-Semantic-Audit` |
| :--- | :--- | :--- | :--- |
| `STD-009-R01` | Anti-confabulation reporting rules in `AGENTS.md` | CLI rejects `VERIFIED` CR status if `verification_evidence` empty | Reviewer verifies cited commands match CI logs |
| `STD-009-R02` | Hard ban on `--no-verify` & test skipping | Git hook / diff scanner flags newly added `.skip`/`#[ignore]` or deleted test files | Audit inspects test assertion diffs |
| `STD-009-R03` | Test-with-change rule in verification playbook | Diff check warns if `src/` mutated with zero `test` file changes | Audit verifies test covers `REQ-*` criteria |
| `STD-009-R04` | Pre-closure CLI run instruction | `pre-commit`, `pre-push` & CI run `aisdgs validate` (`Exit 0` required) | — |
| `STD-009-R05` | Audit trigger rules for `CR-FULL` | Validator checks `quality/reports/AUDIT-<CR>.md` exists in `STRICT` tier | Core execution of `L3` semantic review rubric |
| `STD-009-R06` | Explicit refusal script when told to skip tests | CI blocks unverified commits even if bypassed locally | — |
| `STD-009-R07` | Release checklist in operational docs | `aisdgs report` / `validate` checks zero active/emergency CRs & zero expired waivers | — |
| `STD-009-R08` | Onboarding instruction for `hooks install` | `aisdgs status` checks `.git/hooks/pre-commit` & CI workflow presence | — |

---

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-009` is verified when:
1. Every `VERIFIED` or `CLOSED` `CR-*` contains concrete, non-empty `verification_evidence`.
2. `aisdgs validate` and target automated tests pass cleanly in CI (`STANDARD`/`STRICT`) or local verification (`LITE`).
3. Zero unauthorized skipped/deleted tests or `--no-verify` bypasses occur in governed history.
