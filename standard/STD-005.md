# STD-005 — REQUIREMENTS ENGINEERING & BASELINE MANAGEMENT

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-005` defines how functional, non-functional, data, integration, and security requirements are specified, verified for testability, assembled into a cryptographic Project Baseline (`governance/PROJECT-BASELINE.md`), and guarded against unauthorized drift.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Atomic Requirement:** A single, indivisible capability or constraint (`REQ-*`) that can be verified independently as pass/fail without hidden compound assumptions.
- **Baseline Manifest:** The machine-readable inventory inside `governance/PROJECT-BASELINE.md` recording the baseline version, lock state (`UNINITIALIZED`, `ANCHORED`, `LOCKED`, `DRIFT_DETECTED`), approving Human Authority, and SHA-256 digests of all baselined governance, specification, and contract files.
- **Protected Baseline Artifact:** Any file listed in the Baseline Manifest or matched by `protected_paths` in `.aisdgs/config.yaml`.

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`HUM-PROD`:** Approves `REQ-FUNC-*` functional requirements and acceptance criteria.
- **`HUM-ARCH`:** Approves `REQ-NFUNC-*`, `REQ-DATA-*`, and `REQ-INT-*` requirements and contract specifications.
- **`HUM-SEC`:** Approves `REQ-SEC-*` security and privacy requirements.
- **`HUM-OWNER`:** Authorizes `PROJECT-BASELINE.md` locks (`ANCHORED` or `LOCKED`) and holds fallback authority where roles collapse.
- **`AI-ANALYST` / `AI-STEWARD`:** Elicit requirements, flag ambiguity or contradictions, draft `REQ-*` items (`DRAFT`), and run `aisdgs baseline diff|verify`, but MUST NOT lock or overwrite an approved baseline without human authorization.

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-005-R01` `[WAIVABLE]` — Five-Category Requirement Taxonomy:** Governed requirements MUST be classified into one of five canonical prefixes:
  - `REQ-FUNC-*`: User/system functional behavior and business rules.
  - `REQ-NFUNC-*`: Performance, latency, reliability, scalability, maintainability, UX/accessibility constraints.
  - `REQ-SEC-*`: Authentication, authorization, encryption, auditability, secret isolation, privacy controls.
  - `REQ-DATA-*`: Domain data invariants, retention, schema integrity, migration safety.
  - `REQ-INT-*`: External API, webhook, hardware, or third-party service contracts.
- **`STD-005-R02` `[WAIVABLE]` — Testable & Unambiguous Requirement Quality:** Every `APPROVED` `REQ-*` item MUST specify: (a) canonical ID, (b) concise normative statement (`MUST`/`SHOULD`), (c) priority/criticality, and (d) explicit, falsifiable **Acceptance Criteria** verifiable by automated test, deterministic inspection, or reproducible scenario check. Subjective phrases without measurable bounds (*"fast"*, *"user-friendly"*, *"robust"*) are non-compliant in `STANDARD` and `STRICT` tiers.
- **`STD-005-R03` `[NON-WAIVABLE]` — Mandatory Approved Baseline Gate:** No project MAY execute `FEATURE_REQUEST` implementation against governed modules while `baseline_state` is `UNINITIALIZED`. Implementation requires either `LOCKED` state (`GREENFIELD` / `ITERATIVE`) or `ANCHORED` state (`BROWNFIELD` with Govern-on-Touch rules).
- **`STD-005-R04` `[NON-WAIVABLE]` — Cryptographic Baseline Manifest (`PROJECT-BASELINE.md`):** `governance/PROJECT-BASELINE.md` MUST record in machine-readable YAML frontmatter or structured manifest block:
  - `baseline_version` (SemVer)
  - `baseline_state` (`UNINITIALIZED` | `ANCHORED` | `LOCKED` | `DRIFT_DETECTED`)
  - `approved_by` (`HUM-*` identity) and `locked_at` timestamp
  - `artifacts`: array of `{ path, id (optional), version (optional), sha256 }` covering `PROJECT-CONSTITUTION.md`, `.aisdgs/config.yaml`, `.aisdgs/adoption-profile.yaml`, and all `APPROVED` specifications/contracts in scope.
- **`STD-005-R05` `[NON-WAIVABLE]` — Unauthorized Baseline Drift Prohibition:** Modifying, renaming, or deleting any file recorded in `PROJECT-BASELINE.md` `artifacts` (or matching `protected_paths`) without an active `APPROVED` or `IN_PROGRESS` Change Request (`CR-*`) covering that path MUST cause `aisdgs baseline verify` and `aisdgs validate` to fail (`Exit Code 1` / `Exit Code 3`).
- **`STD-005-R06` `[WAIVABLE]` — Requirement Conflict & Completeness Check Prior to Lock:** Before locking a baseline increment, all `REQ-*` items in scope MUST be checked for internal contradiction, missing dependencies, and alignment with active `ADR-*` boundaries. Conflicting `APPROVED` requirements MUST NOT coexist simultaneously.
- **`STD-005-R07` `[NON-WAIVABLE]` — Human-Authorized Baseline Re-Locking:** Recomputing SHA-256 digests via `aisdgs baseline lock` to absorb new or modified specs MUST occur ONLY at initial baseline approval or upon verified completion of an authorized `CR-*` (or `GOVERNANCE_OR_DOC_SYNC` `PATCH` fix), never automatically by an AI agent to silence a drift error.
- **`STD-005-R08` `[WAIVABLE]` — Baseline Version Increment Discipline:** Every `aisdgs baseline lock` MUST increment `baseline_version` following SemVer (`MAJOR` for architectural/breaking contract shifts, `MINOR` for feature/requirement additions, `PATCH` for non-behavioral doc fixes) and append an audit entry to `changes/CHANGELOG-GOVERNANCE.md`.

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 Establishing or Updating a Baseline
1. Author or update required `PROJECT-CONSTITUTION.md`, `REQ-*`, `ADR-*`, and contract artifacts; ensure `status: APPROVED` following human review.
2. Execute `aisdgs validate` to confirm zero schema, ID, or reference errors.
3. Under human instruction/authorization, execute `aisdgs baseline lock` to compute deterministic SHA-256 digests (normalized LF line endings for cross-OS Windows/Linux/macOS determinism) into `governance/PROJECT-BASELINE.md`.
4. Commit the locked baseline to version control.

### 5.2 Continuous Drift Detection (`aisdgs baseline verify` & `diff`)
1. Recompute normalized SHA-256 hashes for every entry in `PROJECT-BASELINE.md`.
2. Compare against recorded hashes and inspect `git status` / `git diff` on `protected_paths`.
3. If mismatches exist:
   - Check whether each mutated path is declared in `affected_files` / `affected_docs` of a currently `APPROVED` or `IN_PROGRESS` `CR-*`.
   - If covered by an authorized active CR: report `AMENDING (Authorized by CR-XXXX)` (`Exit Code 0` during local WIP; blocks final merge until re-locked).
   - If uncovered: report `DRIFT_DETECTED` (`Exit Code 1`) listing exact drifted paths.

## 6. PROPORTIONAL TIER SCALING RULES

| Dimension | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| `REQ-*` Storage | Structured table/sections inside `PROJECT-BASELINE.md` (or discrete files if preferred) | Discrete files under `docs/requirements/` | Discrete files + mandatory `REQ-SEC-*` & `REQ-NFUNC-*` coverage |
| Baseline Hash Scope | `PROJECT-CONSTITUTION.md`, `.aisdgs/*.yaml`, `PROJECT-BASELINE.md` specs | All `LITE` + all `docs/{requirements,architecture,contracts}/**` | All `STANDARD` + native schema files (`.sql`, `openapi.yaml`, `.proto`) + CI configs |
| LF-Normalized Hashing | Mandatory (cross-OS Git compatibility) | Mandatory | Mandatory |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-005-R03`, `STD-005-R04`, `STD-005-R05`, and `STD-005-R07` are **`[NON-WAIVABLE]`**.
- Emergency production hotfixes (`CR-EMERGENCY` under `STD-012`) MAY temporarily diverge from locked contracts during active mitigation, provided baseline synchronization and re-locking occur within the mandatory reconciliation window (`≤ 72 hours`).

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-005` is verified when:
1. `governance/PROJECT-BASELINE.md` validates against `baseline.schema.json` with state `ANCHORED` or `LOCKED`.
2. `aisdgs baseline verify` exits `0` across Windows (CRLF working tree normalized to LF) and POSIX environments.
3. Every `APPROVED` `REQ-*` possesses explicit acceptance criteria.
