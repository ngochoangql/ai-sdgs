# STD-007 — PROJECT ADOPTION, ONBOARDING MODES & LIFECYCLE GOVERNANCE

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-007` defines the operational procedures for onboarding new (`GREENFIELD`), pre-existing (`BROWNFIELD`), and incrementally evolving (`ITERATIVE`) software repositories onto AI-SDGS, managing pinned standard snapshots, and upgrading Adoption Tiers or standard versions safely without overwriting project baselines.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Govern-on-Touch:** The Brownfield rule allowing untouched legacy modules to operate without upfront retroactive specifications while requiring any module targeted by a feature, contract, or architectural mutation to capture a verified micro-baseline before modification.
- **Standard Upgrade Plan:** A deterministic compatibility diff produced before upgrading `.aisdgs/standard/` from one AI-SDGS release version to another.

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`HUM-OWNER`:** Approves initial project registration, Adoption Tier (`LITE` | `STANDARD` | `STRICT`), Onboarding Pathway (`GREENFIELD` | `BROWNFIELD` | `ITERATIVE`), Tier promotions, and AI-SDGS standard version upgrades.
- **`HUM-ARCH`:** Approves protected path globs, Anchor Baselines in Brownfield onboarding, and migration plans for `MAJOR` AI-SDGS standard upgrades.
- **`AI-STEWARD` / `AI-ANALYST`:** Executes `aisdgs init`, reverse-discovers existing Brownfield structures into `DRAFT` inventories, generates `aisdgs update plan` reports, and runs post-onboarding validation.

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-007-R01` `[NON-WAIVABLE]` — Explicit Registration & Snapshot Pinning:** Every adopting repository MUST contain `.aisdgs/config.yaml`, `.aisdgs/adoption-profile.yaml`, and `.aisdgs/standard-lock.yaml` recording the exact `standard_version`, LF-normalized SHA-256 digests of all installed Level 1 files, selected `adoption_tier`, `onboarding_mode`, and `installed_at` date.
- **`STD-007-R02` `[WAIVABLE]` — Tier-Proportional Directory Materialization:** `aisdgs init` and project onboarding MUST materialize ONLY the directories and files required by the selected `adoption_tier` and active domain contracts—never generating empty placeholder subdirectories (`docs/ui-ux/`, `docs/database/`, etc.) for capabilities the project does not possess.
- **`STD-007-R03` `[NON-WAIVABLE]` — Greenfield Pre-Implementation Gate:** Repositories initialized in `GREENFIELD` mode MUST complete discovery, approve `PROJECT-CONSTITUTION.md`, approve foundational requirements (`REQ-*`) and core architecture (`ADR-001`), and reach `baseline_state: LOCKED` before executing `FEATURE_REQUEST` code implementation.
- **`STD-007-R04` `[NON-WAIVABLE]` — Brownfield Anchor Baseline & Protected Boundary Lock:** Repositories initialized in `BROWNFIELD` mode MUST establish `baseline_state: ANCHORED` prior to AI-assisted feature mutations by locking: (a) `PROJECT-CONSTITUTION.md`, (b) critical `protected_paths` (migrations, auth, public contracts, CI/CD), and (c) known system-level architectural invariants (`ADR-001`).
- **`STD-007-R05` `[WAIVABLE]` — Brownfield Govern-on-Touch Rule:** Under `baseline_state: ANCHORED`, spec-restoring `BUG_FIX` work MAY proceed immediately within `protected_paths` rules; however, any `FEATURE_REQUEST`, `TECHNICAL_CHANGE`, or `ARCHITECTURAL_CHANGE` touching an undocumented legacy module MUST capture and approve that module's current contract/requirements slice (`REQ-*` / `ADR-*`) inside the authorizing `CR-*` prior to code mutation.
- **`STD-007-R06` `[WAIVABLE]` — Iterative Vertical-Slice Baselining:** Repositories in `ITERATIVE` mode MUST lock system-wide architectural and security invariants upfront (`baseline_state: LOCKED`), and MAY introduce feature requirements (`REQ-*`) incrementally per vertical slice provided each slice's specification is approved and locked before slice coding begins.
- **`STD-007-R07` `[NON-WAIVABLE]` — Non-Destructive Standard Upgrades:** Upgrading AI-SDGS to a newer `standard_version` MUST NEVER silently overwrite `governance/PROJECT-CONSTITUTION.md`, `governance/PROJECT-BASELINE.md`, `governance/EXCEPTIONS.md`, `docs/**`, or `changes/**`. `MAJOR` standard upgrades MUST produce an explicit migration plan (`aisdgs update plan`) and obtain `HUM-OWNER` approval before mutating `.aisdgs/standard-lock.yaml`.
- **`STD-007-R08` `[WAIVABLE]` — Monotonic History Preservation on Tier Changes:** Promoting a project from `LITE` → `STANDARD` → `STRICT` MUST preserve all existing `REQ-*`, `ADR-*`, `CR-*`, and `EXC-*` identifiers intact. Downgrading a Tier (e.g., `STANDARD` → `LITE`) requires an explicit `HUM-OWNER` record in `CHANGELOG-GOVERNANCE.md` stating the business rationale.

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 Onboarding Workflow by Mode
1. **Run Initialization:** `aisdgs init --tier <tier> --mode <greenfield|brownfield|iterative>`.
2. **Configure Boundaries:** Populate `.aisdgs/config.yaml` (`protected_paths`, `HUM-*` owners, active adapters) and `.aisdgs/adoption-profile.yaml`.
3. **Establish Initial Baseline:**
   - *Greenfield / Iterative:* Author constitution + initial `REQ-*` + `ADR-001` → human sign-off → `aisdgs baseline lock` (`LOCKED`).
   - *Brownfield:* Author constitution + protected globs + `ADR-001` inventory → human sign-off → `aisdgs baseline lock --anchor` (`ANCHORED`).
4. **Synchronize AI Entrypoints:** Run `aisdgs adapter sync` and `aisdgs validate` (`Exit Code 0`).

### 5.2 Safe Standard Version Upgrade Workflow
1. Run `aisdgs update --check` / `aisdgs update plan --to <version>` to inspect added/changed `STD-*` rules and schema migrations.
2. Evaluate impacts against `adoption-profile.yaml` and active `EXC-*` waivers.
3. Upon `HUM-OWNER` approval, update `.aisdgs/standard/`, `.aisdgs/schemas/`, `.aisdgs/policies/`, and `.aisdgs/standard-lock.yaml`, regenerate adapters via `aisdgs adapter sync`, and run `aisdgs validate` before committing.

## 6. PROPORTIONAL TIER SCALING RULES

| Lifecycle Activity | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| Target Onboarding Time | ≤ 15 minutes | ≤ 30–60 minutes (`ANCHORED` Brownfield) | Structured architecture + security onboarding gate |
| `ANCHORED` → `LOCKED` Convergence | Optional (`ANCHORED` may remain for legacy personal tools) | Recommended once core active modules are baselined | Mandatory convergence schedule tracked in `PROJECT-BASELINE.md` |
| Standard Version Upgrade Gate | `HUM-OWNER` commit | `CR-FAST` (`MINOR`/`PATCH`) / `CR-FULL` (`MAJOR`) | `CR-FULL` + CI validation on staging branch |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-007-R01`, `STD-007-R03`, `STD-007-R04`, and `STD-007-R07` are **`[NON-WAIVABLE]`**.
- If a legacy Brownfield module requires urgent security remediation before full micro-baselining can be written, `CR-EMERGENCY` (`STD-012`) takes precedence and defers micro-baselining to the 72-hour post-incident reconciliation window.

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-007` is verified when:
1. `aisdgs status` reports a valid `adoption_tier`, `onboarding_mode`, pinned `standard_version`, and `ANCHORED` or `LOCKED` baseline state.
2. Zero empty template directories exist in the repository.
3. Simulated or real standard upgrades leave project-authored governance and specification files untouched.
