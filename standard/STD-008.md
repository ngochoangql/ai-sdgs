# STD-008 — ARCHITECTURE, TECHNICAL DESIGN & IMPLEMENTATION GOVERNANCE

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-008` governs system architecture boundaries, Architecture Decision Records (`ADR-*`), third-party dependency introduction, database schema and public API contract mutations, and AI implementation discipline so day-to-day coding preserves structural integrity across arbitrary programming languages and frameworks.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Architectural Invariant:** A structural rule declared in `PROJECT-CONSTITUTION.md` or an `APPROVED` `ADR-*` (e.g., *"domain core MUST NOT import infrastructure/HTTP packages"*, *"all tenant queries MUST enforce `tenant_id` scoping"*).
- **Public Contract:** Any external or cross-module interface depended upon by external clients, persistent storage, or separate deployable units (REST/GraphQL/gRPC specs, CLI flags, event schemas, database tables/migrations).
- **Shadow Dependency:** Any third-party library, SDK, container image, binary, or external network API added to build manifests (`package.json`, `Cargo.toml`, `go.mod`, `pyproject.toml`, `*.csproj`, etc.) or vendored into source code without governance authorization.

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`HUM-ARCH`:** Approves `ADR-*` records, module topology changes, third-party dependency additions, and breaking DB/API contract changes.
- **`HUM-SEC`:** Co-approves dependencies or architectural patterns introducing network egress, cryptography, authentication, or privileged OS access (`STRICT` tier or `HIGH` risk).
- **`AI-ANALYST`:** Drafts `ADR-*` options and trade-off analyses (`DRAFT`), evaluates dependency/migration impacts.
- **`AI-IMPL`:** Writes production and test code strictly inside approved module boundaries, dependency manifests, and contract definitions.

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-008-R01` `[WAIVABLE]` — Mandatory Architecture Decision Records (`ADR-*`):** Every significant architectural choice—including core tech stack, module layering/boundaries, communication protocols, state/persistence strategy, authentication architecture, and cross-cutting error/concurrency models—MUST be recorded in an `ADR-XXXX` artifact containing: (a) Context & Problem, (b) Considered Alternatives (at least 2), (c) Chosen Decision & Normative Invariants, and (d) Consequences & Trade-Offs.
- **`STD-008-R02` `[NON-WAIVABLE]` — Prohibition of Silent Architectural Drift:** AI agents MUST NOT introduce cross-layer imports, new architectural patterns, secondary persistence engines, or undocumented background daemons that violate an `APPROVED` `ADR-*` or `PROJECT-CONSTITUTION.md`. Modifying an approved architectural invariant requires an approved `CR-FULL` (`ARCHITECTURAL_CHANGE`) and a new `ADR-*` superseding the prior decision (`STD-003-R06`).
- **`STD-008-R03` `[NON-WAIVABLE]` — Third-Party Dependency Governance (Zero Shadow Dependencies):** AI agents MUST NOT add, swap, or major-upgrade external runtime or build dependencies in package manifests (or copy third-party code into `src/`) without explicit authorization (`TECHNICAL_CHANGE` under `STD-006`). Dependency proposals MUST justify: necessity over standard library, maintenance health, license compatibility, and security footprint.
- **`STD-008-R04` `[NON-WAIVABLE]` — Database & Persistent State Change Control:** Any modification to persistent schemas, migrations, indexes, or data lifecycle rules MUST be treated as a `TECHNICAL_CHANGE` (`protected_paths`), explicitly documenting forward migration safety, backward compatibility during rolling deploy (if applicable), data-loss risk, and rollback/recovery procedure (`STD-005-R04`, `STD-006-R06`). AI agents MUST NOT edit or rewrite already-applied historical migration files unless explicitly authorized by `HUM-ARCH`.
- **`STD-008-R05` `[WAIVABLE]` — Contract-First Interface Discipline:** Modifications to public APIs, IPC/event schemas, CLI flags, or shared DTO contracts SHOULD update the authoritative contract specification (`docs/contracts/**` or native `openapi.yaml`/`.proto`/`.graphql`) **before or atomically with** handler code, flagging breaking vs. non-breaking compatibility impact.
- **`STD-008-R06` `[WAIVABLE]` — Scoped Implementation Containment:** During `AI-IMPL` execution, code edits MUST stay strictly within the directories/files authorized by the active task or `CR-*`, preserving existing project idioms, naming conventions, error handling, and logging structures rather than reformatting unrelated code or inventing competing patterns.
- **`STD-008-R07` `[WAIVABLE]` — Prohibition of Hardcoded Environment & Magic Hacks:** Implementation code MUST NOT embed environment-specific URLs, magic bypass flags, commented-out dead blocks, or unapproved feature toggles to force tests to pass.
- **`STD-008-R08` `[WAIVABLE]` — Native Architecture Linter Integration:** Where the target language ecosystem supports deterministic boundary linters (e.g., `eslint-plugin-boundaries`, `depguard`, ArchUnit, Rust workspace visibility, Python `import-linter`), projects in `STANDARD` and `STRICT` tiers SHOULD wire those checks into `CI` alongside `aisdgs validate` to upgrade architectural invariants from `L3` to `L2`.

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 Introducing or Changing an Architectural Decision (`ADR-*`)
1. Trigger `ARCHITECTURAL_CHANGE` classification → create `CR-XXXX` (`track: FULL`).
2. Author `docs/architecture/ADR-XXXX-<slug>.md` (`status: DRAFT`) evaluating ≥ 2 viable options and explicit invariants.
3. Obtain `HUM-ARCH` approval → mark new `ADR-XXXX` `APPROVED` (and prior superseded ADR `SUPERSEDED` with `superseded_by: ADR-XXXX`).
4. Execute authorized code changes, verify tests + `aisdgs audit`, and re-lock `PROJECT-BASELINE.md`.

### 5.2 Adding an External Dependency or DB Migration
1. Classify as `TECHNICAL_CHANGE` and check `.aisdgs/config.yaml` `protected_paths` (which MUST include package manifests like `**/package.json`, `**/Cargo.toml`, `**/go.mod`, `**/pyproject.toml`, `**/*.csproj` and migration folders).
2. Create required CR (`CR-FAST` in `LITE`; `CR-FULL` in `STANDARD`/`STRICT`), document dependency/migration risk & rollback, and obtain `HUM-ARCH` / `HUM-OWNER` sign-off before mutating manifests or schema files.

## 6. PROPORTIONAL TIER SCALING RULES

| Governance Area | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| Foundational `ADR-*` (`R01`) | `ADR-001` (stack & module rules) inside `PROJECT-BASELINE.md` or single file | Discrete `docs/architecture/ADR-*.md` for core decisions | Discrete `ADR-*.md` + mandatory architecture boundary checks |
| New Dependency Gate (`R03`) | `CR-FAST` + `HUM-OWNER` confirmation | `CR-FULL` + `HUM-ARCH` license/security check | `CR-FULL` + `HUM-ARCH` & `HUM-SEC` + lockfile vulnerability scan |
| DB Schema / Migration (`R04`) | `CR-FAST` + backup/rollback note | `CR-FULL` + reversible migration verification | `CR-FULL` + non-destructive expand/contract check + staging dry-run |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-008-R02`, `STD-008-R03`, and `STD-008-R04` are **`[NON-WAIVABLE]`** because silent architecture erosion, shadow dependencies, and unreviewed DB mutations are the primary vectors of irreversible project decay.
- Temporary architectural violations during multi-PR Brownfield strangler-fig refactoring MAY be governed via a time-bounded `EXC-*` linked to an overarching `CR-FULL`.

---

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-008` is verified when:
1. `.aisdgs/config.yaml` includes package manifests, lockfiles, and DB migration paths in `protected_paths`.
2. Every commit modifying package manifests, migrations, or public contracts links to an authorized `CR-*`.
3. All `APPROVED` `ADR-*` artifacts conform to schema and contain zero contradicting active invariants.
