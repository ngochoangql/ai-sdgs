# STD-003 — DOCUMENTATION LIFECYCLE, CLASSIFICATION & VERSIONING

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-003` establishes how project and governance documents are classified, versioned, reviewed, approved, amended, and retired across the software lifecycle so AI agents and human engineers can distinguish authoritative baseline specifications from working drafts or obsolete notes.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Normative Artifact:** A governed document whose requirements bind implementation and compliance (`PROJECT-CONSTITUTION.md`, `PROJECT-BASELINE.md`, `REQ-*`, `ADR-*`, contract specs, active `CR-*` and `EXC-*`).
- **Informative Artifact:** Supporting explanatory material (e.g., onboarding guides, exploration spikes, meeting notes, generated status summaries) that provides context without overriding Normative Artifacts.
- **Derived Artifact:** A synchronized file generated deterministically from authoritative sources (e.g., `CLAUDE.md`, `GEMINI.md`, `.cursor/rules/aisdgs.mdc`, `quality/reports/*`).

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`HUM-OWNER` / `HUM-PROD` / `HUM-ARCH` / `HUM-SEC`:** Hold sole authority to transition Normative Artifacts within their domain to `APPROVED`, `SUPERSEDED`, or `DEPRECATED`.
- **`AI-ANALYST` / `AI-STEWARD`:** MAY create `DRAFT` Normative Artifacts, author Informative Artifacts, regenerate Derived Artifacts via `aisdgs adapter sync`, and apply authorized edits to `AMENDING` documents linked to an `APPROVED` Change Request.

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-003-R01` `[NON-WAIVABLE]` — Explicit Artifact Classification:** Every governed document in an AI-SDGS project MUST belong unambiguously to one of four classes:
  1. **`CONSTITUTIONAL`** (`governance/PROJECT-CONSTITUTION.md`, `governance/PROJECT-BASELINE.md`, `governance/EXCEPTIONS.md`)
  2. **`NORMATIVE_SPEC`** (`docs/requirements/**`, `docs/architecture/**`, `docs/contracts/**`)
  3. **`GOVERNANCE_RECORD`** (`changes/records/CR-*.md`, `changes/CHANGELOG-GOVERNANCE.md`, `quality/reports/*`)
  4. **`INFORMATIVE_OR_DERIVED`** (`README.md`, exploratory notes, vendor bridge files)
  Informative or Derived artifacts MUST NOT contradict or supersede `CONSTITUTIONAL` or `NORMATIVE_SPEC` artifacts.
- **`STD-003-R02` `[NON-WAIVABLE]` — Canonical Document Status Lifecycle:** Every `CONSTITUTIONAL` and `NORMATIVE_SPEC` artifact MUST declare a valid `status` from the canonical state machine: `DRAFT`, `IN_REVIEW`, `APPROVED`, `AMENDING`, `SUPERSEDED`, or `DEPRECATED`.
- **`STD-003-R03` `[WAIVABLE]` — Prohibition of Implementation Against Unapproved Drafts:** In `STANDARD` and `STRICT` tiers (and for core architecture in `LITE`), AI agents MUST NOT treat a `DRAFT`, `SUPERSEDED`, or `DEPRECATED` specification as Execution Authority for mutating production source code or contracts.
- **`STD-003-R04` `[WAIVABLE]` — Semantic Versioning of Normative Documents:** Every `CONSTITUTIONAL` and `NORMATIVE_SPEC` artifact MUST carry a `MAJOR.MINOR.PATCH` semantic version (`version` field):
  - **`MAJOR` (`X.0.0`):** Breaking contract/architecture shift, incompatible requirement change, or scope reversal (requires `CR-FULL` in `STANDARD`/`STRICT`).
  - **`MINOR` (`0.X.0`):** Backward-compatible requirement addition, new non-breaking option, or bounded scope expansion (`CR-FAST` or `CR-FULL`).
  - **`PATCH` (`0.0.X`):** Typo fix, formatting cleanup, broken-link repair, or non-normative clarification preserving exact behavioral meaning (`GOVERNANCE_OR_DOC_SYNC`).
- **`STD-003-R05` `[NON-WAIVABLE]` — Controlled Mutation of Approved Documents:** Once a document reaches `APPROVED` and is locked into `PROJECT-BASELINE.md`, any `MAJOR` or `MINOR` modification MUST transition through an authorized Change Request (`AMENDING` → verified → `APPROVED` with incremented version), never through silent in-place overwrites that erase history.
- **`STD-003-R06` `[WAIVABLE]` — Safe Retirement (`SUPERSEDED` vs. `DEPRECATED`):** Obsolete normative documents that were part of a historical release baseline SHOULD NOT be hard-deleted without trace; instead, they MUST either be marked `SUPERSEDED` (with mandatory `superseded_by: <ID>` frontmatter) or `DEPRECATED` (retaining historical rationale in Git/archive).
- **`STD-003-R07` `[WAIVABLE]` — Anti-Bloat & Zero Empty Placeholders:** Projects MUST NOT generate empty directories or stub Markdown files containing only headings/`TODO` markers merely to mimic a directory template. Every committed `APPROVED` document MUST contain substantive, actionable content.
- **`STD-003-R08` `[WAIVABLE]` — Synchronous Documentation-Code Updates:** Any Change Request mutating behavior, contracts, or module boundaries MUST update all affected `NORMATIVE_SPEC` artifacts in the **same atomic change unit / PR** before the CR transitions to `VERIFIED`.

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 Authoring & Approving a New Specification
1. Create artifact with valid YAML frontmatter (`status: DRAFT`, `version: 0.1.0` or `1.0.0`).
2. Complete required content sections with zero `TODO` / placeholder markers.
3. Run `aisdgs validate` (`L2` frontmatter, version format, and link check) and advance to `status: IN_REVIEW`.
4. Upon Human Authority review and sign-off, set `status: APPROVED` (`version: 1.0.0`) and register its SHA-256 hash in `PROJECT-BASELINE.md`.

### 5.2 Amending an Approved Specification
1. Authorize an applicable Change Request (`CR-XXXX`).
2. Update the target specification (optionally marking `status: AMENDING` during multi-commit work), bump `version` according to `STD-003-R04`, and append a summary line to its Change History or `CHANGELOG-GOVERNANCE.md`.
3. Verify code + doc consistency, restore `status: APPROVED`, and run `aisdgs baseline lock`.

---

## 6. PROPORTIONAL TIER SCALING RULES

| Requirement | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| Document Topology | Consolidated specs inside `PROJECT-BASELINE.md` + optional discrete `ADR-*` | Discrete `docs/requirements/`, `docs/architecture/`, `docs/contracts/` | Discrete domain files + immutable historical version audit |
| `DRAFT` Execution Block (`R03`) | Enforced on `PROJECT-CONSTITUTION.md` | Enforced across all `NORMATIVE_SPEC` files | Strictly enforced locally & on CI (`Exit Code 1`) |
| `PATCH` Typo Updates (`R04`) | Direct edit + `baseline lock` permitted | Direct `GOVERNANCE_OR_DOC_SYNC` + PR check | Tracked commit + PR human review |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-003-R01`, `STD-003-R02`, and `STD-003-R05` are **`[NON-WAIVABLE]`**.
- During exploratory prototyping spikes, `STD-003-R03` MAY be waived via `EXC-*` strictly inside isolated spike branches or `experiments/` directories excluded from production builds.

---

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-003` is verified when:
1. All governed Markdown files contain valid `status` and SemVer `version` frontmatter fields.
2. Zero `APPROVED` documents contain unresolved `TODO` / `TBD` placeholder markers or empty required sections.
3. Every `SUPERSEDED` artifact resolves `superseded_by` to an existing `APPROVED` artifact ID.
