# STD-006 — PROPORTIONAL CHANGE CONTROL, IMPACT ANALYSIS & CONFLICT RESOLUTION

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-006` defines how incoming change requests are routed after prompt classification, how blast-radius impact analysis is performed, how competing requirements or parallel changes are arbitrated, and how the proportional two-track Change Request lifecycle (`FAST` vs. `FULL`) prevents cumulative baseline drift without suffocating routine engineering velocity.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Scope Creep (Change Smuggling):** Introducing unrequested or unauthorized feature mutations, dependency additions, or contract changes inside an action classified as `BUG_FIX`, `REFACTORING`, or `QUESTION`.
- **Track Escalation:** Promoting a Change Request's `track` field from `FAST` to `FULL` (preserving its `CR-XXXX` identifier) when impact analysis or implementation uncovers cross-module, contract, dependency, security, or architectural impact.

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`AI-ANALYST`:** Classifies prompts, detects scope/baseline conflicts, executes blast-radius impact analysis, and creates `DRAFT` / `ANALYZED` `CR-XXXX` manifests.
- **`HUM-OWNER` / `HUM-PROD` / `HUM-ARCH` / `HUM-SEC`:** Review impact & risk assessments and grant or deny `APPROVED` execution status according to the Approval Matrix (`DOC-ARCH-003`).
- **`AI-IMPL`:** Executes changes **strictly inside** the `affected_files` / `implementation_scope` authorized by an `APPROVED` CR (or authorized zero-CR `BUG_FIX` / `REFACTORING`).

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-006-R01` `[NON-WAIVABLE]` — Zero-CR vs. Governed-CR Routing:** Every repository-mutating request MUST follow the deterministic routing rules by prompt category:
  - **Zero-CR Path (`QUESTION`, `GOVERNANCE_OR_DOC_SYNC`, spec-restoring `BUG_FIX` in `LITE`/`STANDARD`, single-module contract-preserving `REFACTORING` in `LITE`):** Proceeds without creating a `CR-*` file, provided zero protected contracts, external dependencies, or `REQ-*` semantics are altered.
  - **`FAST` Track (`CR-XXXX` with `track: FAST`):** Applies to bounded `ENHANCEMENT`, multi-file `REFACTORING` (`STANDARD`/`STRICT`), `BUG_FIX` in `STRICT`, or `LITE`-tier `FEATURE_REQUEST` / `TECHNICAL_CHANGE` lacking architectural boundary shifts.
  - **`FULL` Track (`CR-XXXX` with `track: FULL`):** Mandatory for `ARCHITECTURAL_CHANGE` across all tiers, and mandatory in `STANDARD` and `STRICT` tiers for `FEATURE_REQUEST`, `TECHNICAL_CHANGE` (new dependencies, DB migrations, public API changes), security-sensitive changes, or cross-module mutations.
- **`STD-006-R02` `[NON-WAIVABLE]` — Anti-Smuggling & Scope Containment:** An AI agent executing a `BUG_FIX`, `REFACTORING`, or approved `CR-XXXX` MUST restrict file and behavioral modifications to the declared scope. If fixing a bug or implementing a CR requires touching undeclared modules, public contracts, DB schemas, or third-party dependencies, execution MUST pause and either amend the CR scope or escalate via `STD-006-R05`.
- **`STD-006-R03` `[WAIVABLE]` — Mandatory `FAST` Track Attributes (5 Core Fields):** Every `track: FAST` Change Request (`changes/records/CR-XXXX.md`) MUST include valid frontmatter and body covering:
  1. `id` (`CR-[0-9]{4}`) & `track: FAST`
  2. `classification` & trigger summary
  3. `affected_scope` (`affected_requirements`, `affected_files` / globs)
  4. `approval_status` (`DRAFT` | `ANALYZED` | `APPROVED` | `IN_PROGRESS` | `VERIFIED` | `CLOSED` | `REJECTED`) & `approved_by`
  5. `verification_evidence` (populated prior to `VERIFIED` / `CLOSED`)
- **`STD-006-R04` `[WAIVABLE]` — Mandatory `FULL` Track Attributes (14 Fields):** Every `track: FULL` Change Request MUST record:
  1. `id` (`CR-[0-9]{4}`) & `track: FULL`
  2. `request_source` (human requester / incident / audit ID)
  3. `description` & business/technical `justification`
  4. `classification` (canonical prompt category)
  5. `affected_requirements` (`REQ-*` added/modified/retired)
  6. `affected_docs_and_adrs` (`ADR-*`, contract files)
  7. `affected_modules_and_files` (explicit path/glob boundary)
  8. `dependency_impact` (external packages, services, migrations)
  9. `risk_level` (`LOW`|`MEDIUM`|`HIGH`|`CRITICAL`) & `rollback_plan`
  10. `proposed_solution` (including rejected alternatives where non-trivial)
  11. `required_approvals` (`HUM-*` roles) & `approval_status`
  12. `implementation_plan` (ordered execution steps)
  13. `verification_evidence` (test outputs, `aisdgs validate` result)
  14. `closure_summary` (baseline version re-locked)
- **`STD-006-R05` `[NON-WAIVABLE]` — Mandatory Track Escalation on Blast-Radius Expansion:** If impact analysis or in-flight coding on a zero-CR task or `track: FAST` CR reveals any trigger requiring `FULL` track (new runtime dependency, public contract/DB breaking change, security boundary touch, or module topology change), the agent MUST halt code mutation, upgrade the record in-place to `track: FULL` (preserving `CR-XXXX` ID), complete full impact analysis, and await required `HUM-*` sign-off.
- **`STD-006-R06` `[WAIVABLE]` — Six-Dimension Impact Analysis (`FULL` Track):** Before requesting `APPROVED` status on a `track: FULL` CR, impact analysis MUST explicitly evaluate: (1) Requirements & Business Logic conflicts, (2) Module & Architectural boundaries, (3) Data Model & Migration compatibility, (4) Public API / Integration backward compatibility, (5) Security, Privacy & Performance regressions, and (6) Test & Documentation synchronization scope.
- **`STD-006-R07` `[WAIVABLE]` — Conflict Detection & Arbitration:** When two proposed CRs, prompts, or requirements conflict (mutating the same contract or asserting incompatible invariants):
  1. Neither conflicting mutation MAY execute silently.
  2. Already `APPROVED` baseline artifacts hold precedence until superseded by a newly `APPROVED` CR.
  3. Concurrent `IN_PROGRESS` CRs touching overlapping `affected_files` MUST declare explicit sequencing or merge-order arbitration approved by `HUM-ARCH` / `HUM-OWNER`.
- **`STD-006-R08` `[NON-WAIVABLE]` — Closure Gate (Sync + Evidence + Re-Lock):** No `CR-*` MAY transition to `CLOSED` until: (a) implementation matches authorized scope, (b) verification evidence is recorded (`STD-009`), (c) all `affected_requirements` / `affected_docs_and_adrs` are synchronized (`STD-003-R08`), and (d) `governance/PROJECT-BASELINE.md` is re-locked (`STD-005-R07`) when baseline artifacts changed.

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 End-to-End `FULL` Change Request Workflow (12 Steps)
1. **Receive & Triage:** Classify incoming prompt (`STD-011`).
2. **Initialize CR:** Run `aisdgs change create --track full` → generates `changes/records/CR-XXXX.md` (`status: DRAFT`).
3. **Identify Scope & Conflicts:** Map touched `REQ-*`, `ADR-*`, contracts, and module paths; check active CR collisions (`R07`).
4. **Analyze Impact & Risk:** Complete 6-dimension impact analysis (`R06`), assign `risk_level` (`STD-002-R02`), and define rollback strategy.
5. **Propose Solution:** Transition CR to `status: ANALYZED` and present concise summary to human authority.
6. **Human Approval Gate:** Obtain explicit `HUM-*` approval (`status: APPROVED`) — or halt if `REJECTED`.
7. **Plan & Execute (`status: IN_PROGRESS`):** Modify code and tests strictly within `affected_modules_and_files`.
8. **Synchronize Specs:** Update affected `REQ-*`, `ADR-*`, and contract docs atomically.
9. **Verify with Evidence:** Run test suite + `aisdgs change verify CR-XXXX` + `aisdgs validate`; record outputs (`status: VERIFIED`).
10. **Re-Lock Baseline & Close:** Under human sign-off, run `aisdgs baseline lock`, append to `CHANGELOG-GOVERNANCE.md`, and set `status: CLOSED`.

## 6. PROPORTIONAL TIER SCALING RULES

| Scenario | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| Spec-Restoring `BUG_FIX` | Zero-CR | Zero-CR (unless touching protected path) | `CR-FAST` required |
| Internal `REFACTORING` | Zero-CR | Zero-CR (single file) / `CR-FAST` (multi-file) | `CR-FAST` required |
| New Feature (`FEATURE_REQUEST`) | `CR-FAST` (compact) | `CR-FULL` mandatory | `CR-FULL` + dual `HUM-PROD`/`HUM-ARCH` sign-off |
| Architectural Change | `CR-FULL` mandatory | `CR-FULL` + `ADR-*` mandatory | `CR-FULL` + `ADR-*` + `HUM-SEC` review |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-006-R01`, `STD-006-R02`, `STD-006-R05`, and `STD-006-R08` are **`[NON-WAIVABLE]`**.
- Active production outages bypass pre-execution `CR-FULL` drafting ONLY via `track: EMERGENCY` under `STD-012`, which mandates retrospective impact reconciliation within 72 hours.

---

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-006` is verified when:
1. All `changes/records/CR-*.md` files validate against `change-request.schema.json` for their declared `track`.
2. `aisdgs change verify <CR-ID>` confirms modified working-tree/branch paths fall within the CR's authorized `affected_files` globs.
3. Zero `CLOSED` CRs leave `PROJECT-BASELINE.md` in `DRIFT_DETECTED` state.
