# STD-004 — SOURCE OF TRUTH, MACHINE-READABLE METADATA & TRACEABILITY

## 1. PURPOSE & GOVERNANCE SCOPE

`STD-004` defines the Single Source of Truth (SSoT) ownership laws, machine-readable YAML frontmatter contract, canonical identifier syntax, and bidirectional traceability graph rules that enable `aisdgs validate` to verify project consistency deterministically without relying on probabilistic LLM interpretation.

---

## 2. TERMS & NORMATIVE DEFINITIONS

- **Single Source of Truth (SSoT):** The rule that every normative statement (requirement, architectural decision, API/DB schema, or governance rule) resides canonically in exactly one authoritative file and is referenced—never copy-pasted as competing normative text—elsewhere.
- **Traceability Graph:** The directed graph connecting `REQ-*` (requirements), `ADR-*` (architecture decisions), contract artifacts, `CR-*` (change records), `EXC-*` (waivers), and verification evidence.
- **Orphan Reference (Dangling Link):** Any identifier citation pointing to a non-existent, misspelled, or retired artifact without a valid replacement chain.

---

## 3. ROLES & AUTHORITY BOUNDARIES

- **`HUM-ARCH` / `HUM-OWNER`:** Designate authoritative contract sources (e.g., whether OpenAPI YAML, Protobuf `.proto`, Prisma/SQL migration, or Markdown spec is SSoT for a given contract).
- **`AI-STEWARD` / `AI-IMPL`:** Maintain accurate YAML frontmatter, preserve stable IDs across edits, and cite `REQ-*`/`ADR-*`/`CR-*` IDs in governed records and commits.

---

## 4. NORMATIVE REQUIREMENTS

- **`STD-004-R01` `[NON-WAIVABLE]` — Single Authoritative Owner Per Concern:** Every governed requirement, architectural decision, data schema, and API contract MUST have a single designated authoritative artifact. Other documents needing that rule MUST link to its canonical ID (`REQ-*`, `ADR-*`, or contract path) rather than duplicating competing normative definitions.
- **`STD-004-R02` `[NON-WAIVABLE]` — Mandatory YAML Frontmatter on Governed Markdown:** Every `CONSTITUTIONAL`, `NORMATIVE_SPEC`, and `GOVERNANCE_RECORD` Markdown file (excluding append-only `CHANGELOG-GOVERNANCE.md`) MUST start with a valid YAML frontmatter block delimited by `---` containing at minimum:
  - `id`: Canonical unique identifier matching `STD-004-R03`.
  - `title`: Human-readable title (`non-empty string`).
  - `version`: SemVer string (`MAJOR.MINOR.PATCH`).
  - `status`: Canonical status enum matching `STD-003-R02` (or CR/Exception status enum).
  - `artifact_class`: `CONSTITUTIONAL` | `NORMATIVE_SPEC` | `GOVERNANCE_RECORD`.
  - `last_updated`: ISO-8601 date (`YYYY-MM-DD`).
- **`STD-004-R03` `[NON-WAIVABLE]` — Canonical Identifier Syntax & Uniqueness:** Every governed entity ID across the repository MUST be globally unique within the project and match its canonical regular expression:
  - Standard: `^STD-(0[0-9]{2}|[1-9][0-9]{2})$`
  - Standard Rule: `^STD-[0-9]{3}-R[0-9]{2}$`
  - Requirement: `^REQ-(FUNC|NFUNC|SEC|DATA|INT)-[0-9]{3,4}$`
  - Architecture Decision: `^ADR-[0-9]{3,4}$`
  - Change Request: `^CR-[0-9]{4}$`
  - Exception Waiver: `^EXC-[0-9]{4}$`
  - Risk Item: `^RISK-[0-9]{3,4}$`
  Identifiers MUST NEVER be reused for a different semantic entity once committed.
- **`STD-004-R04` `[NON-WAIVABLE]` — Referential Integrity (Zero Dangling IDs):** Every identifier listed in frontmatter arrays (`normative_references`, `affected_requirements`, `affected_adrs`, `supersedes`, `superseded_by`, `waives_rules`) MUST resolve to an existing entity in the repository or `.aisdgs/standard/`. Dangling references MUST fail `aisdgs validate` (`Exit Code 1`).
- **`STD-004-R05` `[WAIVABLE]` — Acyclic Normative Reference Graph:** Normative dependency chains (`normative_references`) MUST form a Directed Acyclic Graph (DAG). Circular normative dependencies (`A` normatively depends on `B` while `B` normatively depends on `A`) are prohibited (`Exit Code 1`). Mutual awareness links MUST use an informative `related_artifacts` field instead.
- **`STD-004-R06` `[WAIVABLE]` — End-to-End Change Traceability Chain:** Every `CR-FULL` (and `CR-FAST` touching `REQ-*`) MUST establish an unbroken machine-verifiable chain:
  `Trigger Source` → `CR-XXXX` → `Affected REQ-* / ADR-* / Contract` → `Modified Repository Files / Commits` → `Verification Evidence`.
- **`STD-004-R07` `[WAIVABLE]` — Native Contract Schema Delegation:** When a project uses machine-executable interface or database definitions (e.g., `openapi.yaml`, `.proto`, `.graphql`, SQL migrations, JSON Schema), `docs/contracts/` SHOULD register those native files directly in `PROJECT-BASELINE.md` as the SSoT rather than forcing manual prose duplication of every field in Markdown.
- **`STD-004-R08` `[WAIVABLE]` — Commit & PR Identifier Tagging:** Commits and Pull Requests executing a Change Request SHOULD include the canonical ID in the commit header or trailer (e.g., `feat(auth): add SSO callback [CR-0014]`) so `aisdgs audit` and Git history link code diffs deterministically to authorization records.

---

## 5. OPERATIONAL PROCEDURES & WORKFLOWS

### 5.1 Assigning & Registering Canonical IDs
1. Inspect existing artifacts in the target domain (`docs/requirements/`, `docs/architecture/`, `changes/records/`) or run `aisdgs status` to determine the next monotonically increasing sequence number.
2. Assign the new ID in YAML frontmatter (or inline anchor table in `LITE` tier `PROJECT-BASELINE.md`).
3. Run `aisdgs validate` to confirm global uniqueness and regex conformance.

### 5.2 Deterministic Graph Validation (`aisdgs validate`)
1. Parse YAML frontmatter across all governed Markdown files and structured inline tables in `PROJECT-BASELINE.md`.
2. Build an in-memory symbol table mapping `ID → {file_path, artifact_class, status, version}`.
3. Detect duplicate IDs, regex mismatches, dangling references (`R04`), cycles in `normative_references` (`R05`), and illegal links to `DEPRECATED`/`SUPERSEDED` targets without active waivers.

## 6. PROPORTIONAL TIER SCALING RULES

| Dimension | `TIER-1: LITE` | `TIER-2: STANDARD` | `TIER-3: STRICT` |
| :--- | :--- | :--- | :--- |
| Frontmatter & IDs (`R02`–`R04`) | Mandatory on `PROJECT-CONSTITUTION.md`, `PROJECT-BASELINE.md`, `CR-*`; inline `REQ-*` IDs allowed inside `PROJECT-BASELINE.md` | Mandatory YAML frontmatter across all discrete spec & CR files | Mandatory across all artifacts + 100% `REQ-*` ↔ test/verification trace matrix |
| Native Contract SSoT (`R07`) | Optional | Recommended (`SHOULD`) | Mandatory (`MUST` hash native schema files in baseline) |
| Commit `[CR-XXXX]` Tagging (`R08`) | Optional (`MAY`) | Recommended (`SHOULD`) | Mandatory (`MUST` enforced via `commit-msg` / CI check) |

---

## 7. EXCEPTIONS & ESCALATION RULES

- `STD-004-R01` through `STD-004-R04` are **`[NON-WAIVABLE]`** because deterministic CLI validation cannot function if IDs collide, frontmatter is malformed, or links are broken.
- Legacy Brownfield folders not yet onboarded under Govern-on-Touch (`STD-007`) are outside governed spec paths until their first micro-baseline CR.

## 9. VERIFICATION CRITERIA & REQUIRED EVIDENCE

Compliance with `STD-004` is verified when:
1. `aisdgs validate` parses 100% of governed files with zero YAML syntax or JSON Schema errors.
2. Symbol-table check reports zero duplicate IDs, zero broken references, and zero `normative_references` cycles.
3. Every closed `CR-FULL` resolves cleanly to existing `REQ-*`/`ADR-*` targets and recorded verification evidence.
